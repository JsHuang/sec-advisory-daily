🔴 Dgraph DQL Injection via checkUserPassword GraphQL Query
GHSA-q2m9-6jp9-c6mc | CVE: CVE-2026-44840
优先级: 极高
High ⭐ 21,716 🔴 完整PoC 📖 详细分析

漏洞描述：Dgraph 的 checkUserPassword GraphQL 查询存在 DQL（Dgraph Query Language）注入漏洞。用户提供的密码值通过 fmt.Sprintf 直接插入到 DQL 的 checkpwd() 查询中，没有任何转义或参数化处理。攻击者可以注入包含双引号的密码，突破 DQL 字符串字面量并追加任意 DQL 查询块。

影响产品：github.com/dgraph-io/dgraph ⭐ 21,716

影响版本：≤ v25.3.3（所有包含 GraphQL @secret 指令支持的版本）

攻击面：网络可达，通过任意 GraphQL 端点访问，无需认证（checkUserPassword 是未认证查询）

触发条件：攻击者发送包含特制密码字段的单个 HTTP POST 请求即可触发。漏洞位于 query_rewriter.go（约第364行），密码通过 fmt.Sprintf 直接拼接到 DQL 查询中。

潜在危害：

  • 数据枚举：注入的查询块在服务端执行，可通过 touched_uids 指标探测谓词、类型和节点
  • Schema 发现：攻击者可枚举数据库中所有谓词和类型
  • 资源耗尽：昂贵的注入查询（递归遍历、大聚合）在 DQL 层执行，消耗服务器资源
  • 潜在数据泄露：取决于 Dgraph 配置，注入查询结果可能泄露到响应中

可利用性：有完整PoC — 公告包含完整的 curl 命令、漏洞代码路径分析、修复建议代码

修复建议：升级到 v25.3.4。临时缓解：在密码值嵌入 DQL 查询前转义双引号和反斜杠字符，或实施参数化查询支持。

🔴 Kanidm SCIM Filter Stack Exhaustion DoS (Process Abort)
GHSA-r5fr-9gmv-jggh | CVE: CVE-2026-46689
优先级: 极高
High ⭐ 5,081 🔴 完整PoC 📖 详细分析

漏洞描述：Kanidm 身份管理服务器的 SCIM filter 语法解析器（PEG 递归下降解析器）没有深度限制。单个未认证的 GET 请求，携带约 4-12 KB 的嵌套括号 filter 查询字符串，即可使解析器超过工作线程的栈保护页。Rust 对栈溢出的响应是 std::process::abort()——整个 kanidmd 进程退出。

影响产品：github.com/kanidm/kanidm ⭐ 5,081

影响版本：v1.7.0 至 master @ edf50b9da（scim_proto ≤ 1.9.2, kanidm_proto ≤ 1.9.2）

攻击面：网络可达，无需认证。解析在 axum 的 Query 提取器中执行，在 ACL 检查之前。9个 SCIM 端点受影响。

触发条件：发送约 3000 层嵌套括号的 GET 请求（~4KB payload），例如：
GET /scim/v1/Application?filter=(((((...(a pr)...))))
Release 构建阈值约 2000 层嵌套 / ~4KB。6011 字节版本可绕过 nginx 默认 8KB header 限制。

潜在危害：

  • 进程级服务中断：栈溢出触发 std::process::abort()，所有进行中的 HTTP 请求、OAuth2/OIDC 会话、LDAP 绑定和 Web UI 全部终止
  • 可重复利用：一个 ~12KB GET 请求即可导致一次崩溃，循环发送可持续使服务不可用
  • tokio 的 per-task catch_unwind 隔离不适用于 abort

可利用性：有完整PoC — 包含 curl 命令、源码分析（PEG 语法递归规则）、基准测试数据、testkit 端到端验证

修复建议：升级到 v1.9.3。在 PEG 解析前添加长度/深度预检查，或降低 hyper 的 max_buf_size。临时缓解：在反向代理层限制 filter 参数长度。

🟠 Scriban array.insert_at DoS - 绕过 LoopLimit 和 LimitToString
GHSA-24c8-4792-22hx | CVE: N/A
优先级: 高
High ⭐ 3,911 🔴 完整PoC 📖 详细分析

漏洞描述：Scriban 模板引擎的 ArrayFunctions.InsertAt 在 C# 的 for 循环中分配 index - list.Count 个 null 条目，对 index 没有上限。该函数作为模板内置函数 array.insert_at 暴露给模板作者，填充循环忽略了所有现有安全控制：LoopLimit、LimitToString、ObjectRecursionLimit 和 RecursiveLimit。单个模板如 {{ [1] | array.insert_at 200000000 'x' | array.size }} 在 1GB 内存的主机上不到一秒即可导致 OutOfMemoryException。

影响产品：github.com/scriban/scriban ⭐ 3,911

影响版本：scriban ≤ 7.1.0, Scriban.Signed ≤ 7.1.0

攻击面：任何渲染攻击者控制或影响的 Scriban 模板的主机（邮件模板、报告模板、CMS 模板、静态站点生成器等）

触发条件：一行模板 payload 即可触发，例如：
{{ [1] | array.insert_at 2147483647 'x' | array.size }}
即使 LoopLimit=10、LimitToString=100 也无法防护（循环在编译后的 C# 中执行，不经过 StepLoop）

潜在危害：

  • OOM 终止整个进程（ASP.NET 主机下所有租户受影响）
  • 即使 OOM 被抑制，GC 压力也会导致进程挂起数十秒
  • ~600ms 即可在 1GB Docker 容器中触发

可利用性：有完整PoC — 包含完整 .NET 9 项目代码、Docker 复现步骤、基准测试数据、源码分析和修复代码建议

修复建议：添加 context-aware 重载，在填充循环运行前验证 index 是否超过 LoopLimit。参照 ArrayFunctions.AddRange、Compact 等已修复函数的模式。

🟠 TYPO3 Content Element Selector PHP 反序列化 RCE
GHSA-8x3j-439w-537c | CVE: CVE-2026-46725
优先级: 高
Critical ⭐ 57 📖 详细分析

漏洞描述：TYPO3 的 "Content Element Selector" (ceselector) 扩展将攻击者控制的 cookie 直接传递给 PHP 的 unserialize()，没有安全处理输入。远程未认证攻击者可提供特制的序列化 payload 触发 PHP 对象注入，导致 TYPO3 服务器上的远程代码执行。利用需要内容元素配置为 "Persistent Mode: Static"。

触发条件：需要 ceselector 插件配置为 "Persistent Mode: Static"

潜在危害：远程代码执行——攻击者可在服务器上执行任意命令

可利用性：有详细原理——描述了攻击路径（Cookie → unserialize → PHP Object Injection → RCE），需要特定配置条件

修复建议：升级到 ceselector 3.0.3、4.0.2、5.0.1 或 6.0.1
