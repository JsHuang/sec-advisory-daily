🔴 Nest: Middleware Bypass on Fastify via Trailing Slash
GHSA-6v32-fjc9-9qf6 | CVE: CVE-2026-54281
优先级: 12/15
High ⭐ 76,142 🔴 PoC Available 📖 详细分析

漏洞描述：NestJS 的 Fastify 适配器（@nestjs/platform-fastify）存在中间件绕过漏洞。当通过 MiddlewareConsumer.forRoutes() API 注册中间件时，未认证的客户端只需在请求 URL 末尾添加一个尾部斜杠 / 即可绕过该路由的中间件。这意味着认证、授权、日志记录等关键中间件可以被完全跳过。

影响产品：NestJS (@nestjs/platform-fastify) ⭐ 76,142

影响版本：<= 11.1.23

修复版本：11.1.24

攻击面：所有使用 Fastify 适配器并注册了路由中间件的 NestJS 应用。攻击者仅需知道目标路由路径，即可通过追加 / 绕过中间件保护。无需任何特殊配置或前置条件。

触发条件：应用使用 @nestjs/platform-fastify 适配器 + 通过 MiddlewareConsumer.forRoutes() 注册中间件。在默认 Fastify 配置下即可触发，无需特殊配置。

潜在危害：

  • 绕过认证中间件，未授权访问受保护的 API 端点
  • 绕过授权检查，实现权限提升
  • 绕过审计日志，隐藏恶意操作痕迹
  • 绕过速率限制，实施暴力破解或 DoS

可利用性：有完整 PoC。攻击方法极其简单——只需在 URL 末尾加一个 /。该漏洞在最新发行版（11.1.24）上被确认存在，影响面覆盖所有使用 Fastify 适配器的 NestJS 项目。

修复建议：

  • 立即升级 @nestjs/platform-fastify 到 11.1.24 或更高版本
  • 审查所有中间件注册方式，确认关键中间件是否覆盖了尾部斜杠路径
  • 检查访问日志，排查是否有利用此漏洞绕过中间件的痕迹
  • 考虑在反向代理层额外添加路径规范化处理

🔴 LiteLLM: Authentication Bypass via Host Header Injection
GHSA-4xpc-pv4p-pm3w | CVE: CVE-2026-49468
优先级: 12/15
Critical ⭐ 53,968 🔴 PoC Available 📖 详细分析

漏洞描述：LiteLLM 代理存在 Host 头解析缺陷，在特定条件下可允许未认证访问受保护的管理路由。认证层通过 litellm/proxy/auth/auth_utils.py::get_request_route() 中的 request.url.path 推导有效路由，而 Starlette 框架会根据 Host 头重建 URL。攻击者构造恶意 Host 头可使认证网关评估与实际 FastAPI 分发路由不同的路径，从而绕过认证。

影响产品：LiteLLM ⭐ 53,968

影响版本：< 1.84.0

修复版本：1.84.0

攻击面：暴露在网络上的 LiteLLM 代理实例。攻击者需能够向目标发送 HTTP 请求并控制 Host 请求头。在反向代理未强制覆盖 Host 头的部署场景下尤其危险。

触发条件：

  • LiteLLM 代理直接暴露于网络（无反向代理或反向代理未规范化 Host 头）
  • 攻击者可控制 HTTP 请求的 Host 头字段
  • 存在受保护的管理路由

潜在危害：

  • 未授权访问 LiteLLM 管理 API，可能修改配置、API Key
  • 窃取 LLM API 密钥和模型配置
  • 劫持 AI 推理请求，实施提示注入或数据泄露
  • 在 AI 基础设施中建立持久化后门

可利用性：有详细原理。公告明确指出了漏洞代码位置（get_request_route()）、利用机制（Host 头注入导致路由混淆），以及触发条件。大多数标准部署（有反向代理）可能不受影响，但直接暴露的实例风险极高。

修复建议：

  • 立即升级到 LiteLLM 1.84.0 或更高版本
  • 确保反向代理（Nginx/Caddy 等）强制覆盖 Host 头
  • 审查网络配置，避免 LiteLLM 代理直接暴露于公网
  • 检查访问日志中是否有异常的 Host 头请求

🟠 Jupyter Server: Stored XSS in NbconvertFileHandler / NbconvertPostHandler
GHSA-fcw5-x6j4-ccmp | CVE: CVE-2026-44727
优先级: 9/15
Critical ⭐ 564 📖 详细分析

漏洞描述：Jupyter Server 中的 nbconvert HTTP 处理器在 Jupyter 源域下渲染用户编写的 notebook HTML，但其 Content-Security-Policy 中缺少 sandbox 指令。结合 nbconvert.HTMLExporter 默认不进行 HTML 清理的行为，包含恶意 HTML 载荷的 notebook（通过 display_data 输出）可触发存储型 XSS，攻击者可获得 cookie 访问权限、完整的 /api/* 权限以及内核远程代码执行能力。

影响产品：Jupyter Server ⭐ 564

影响版本：<= 2.19.0

修复版本：2.20.0

攻击面：多用户 Jupyter 环境（如 JupyterHub）。攻击者创建一个包含恶意 HTML 输出的 notebook，当受害者（其他用户或管理员）通过 nbconvert 渲染该 notebook 时触发。

触发条件：

  • 受害者访问 /nbconvert/html/<path> 渲染攻击者编写的 notebook
  • notebook 中包含带有恶意 HTML 载荷的 display_data 输出
  • CSP 缺少 sandbox 指令，允许脚本在 Jupyter 源域下执行

潜在危害：

  • 存储型 XSS：恶意脚本在 Jupyter 域名下执行
  • Cookie 窃取，会话劫持
  • 利用 /api/* 权限操作 notebook、文件系统
  • 通过 Jupyter Kernel 实现远程代码执行（RCE）

可利用性：有详细原理。公告描述了完整的攻击链路（nbconvert 渲染 → CSP 缺失 sandbox → XSS → cookie 访问 → 内核 RCE），虽然 Star 数较低，但影响严重。Jupyter Server 是 JupyterHub 的核心组件，在多用户环境中影响面更大。

修复建议：

  • 升级 jupyter-server 到 2.20.0 或更高版本
  • 审查 notebook 内容策略，限制不受信任的 HTML 输出
  • 在多用户环境中实施 notebook 内容审计机制

🟠 Avo: Missing Authorization in Association Attach Endpoint
GHSA-8fq9-273g-6mrg | CVE: CVE-2026-55518
优先级: 9/15
Critical ⭐ 1,788 📖 详细分析

漏洞描述：Avo 框架的关联附件工作流存在严重的授权缺陷。虽然 UI 层和 GET /resources/:resource/:id/:related/new 路径会检查 attach_<association>? 权限，但实际执行写入的 POST /resources/:resource/:id/:related 端点在变更关联之前并未执行相同的授权检查。这导致低权限用户可以绕过隐藏/禁用的附件控件，直接通过发送 POST 请求将相关记录附加到父记录。

影响产品：Avo (Ruby on Rails 管理面板框架) ⭐ 1,788

影响版本：<= 3.32.0 或 >= 4.0.0.beta.1 且 < 4.0.0.beta.51

修复版本：3.32.1 / 4.0.0.beta.51

攻击面：所有使用 Avo 构建管理面板并定义了资源关联关系的 Ruby on Rails 应用。任何已认证的低权限用户均可利用此漏洞。

触发条件：

  • 应用使用 Avo 且定义了资源间的关联关系
  • 攻击者拥有有效的低权限用户账户
  • 直接向 POST 端点发送请求，绕过前端 UI 的权限检查

潜在危害：

  • 权限提升：低权限用户可操作本不应有权限的关联数据
  • 数据篡改：将任意记录关联到目标资源，破坏数据完整性
  • 业务逻辑绕过：跳过应用层的数据访问控制

可利用性：有详细原理。公告明确指出了漏洞的精确端点路径（POST /resources/:resource/:id/:related）、缺失的检查（attach_<association>?），以及利用方式（直接发送 POST 请求）。攻击方法简单直接。

修复建议：

  • 升级 Avo 到 3.32.1 或 4.0.0.beta.51 或更高版本
  • 审查所有关联附件操作的授权配置
  • 检查数据库审计日志，排查是否存在异常的关联操作
  • 确保后端 POST 端点与前端 UI 使用相同的权限检查逻辑

🟡 Picklescan: Detection Bypass via idlelib.autocomplete
GHSA-6w4w-5w54-rjvr | CVE: CVE-2025-71358
优先级: 6/15
High ⭐ 418 🔴 PoC Available 📖 详细分析

漏洞描述：Picklescan（Python pickle 文件安全扫描器）存在检测绕过漏洞。攻击者可以在 pickle 文件的 __reduce__ 方法中调用 Python 内置库函数 idlelib.autocomplete.AutoComplete.get_entity 来执行恶意操作。由于 Picklescan 未将此函数标记为危险函数，扫描会通过，受害者在信任扫描结果的情况下加载该 pickle 文件时将触发任意代码执行。

影响产品：Picklescan ⭐ 418

影响版本：< 0.0.29

修复版本：0.0.29

攻击面：依赖 Picklescan 进行 pickle 文件安全扫描的 ML/AI 流水线、数据管道、模型分发系统。攻击者投递一个看似安全的 pickle 文件，通过 Picklescan 扫描后被自动加载。

触发条件：

  • 受害系统使用 Picklescan 扫描 pickle 文件
  • 攻击者构造使用 idlelib.autocomplete.AutoComplete.get_entity 的恶意 pickle
  • 扫描通过后受害者加载（unpickle）该文件

潜在危害：

  • 远程代码执行（RCE）：在受害者系统上执行任意代码
  • 供应链攻击：污染 ML 模型分发管道
  • 数据泄露：窃取训练数据和模型权重

可利用性：有完整 PoC 和详细分析。攻击载荷清晰：在 __reduce__ 中调用 idlelib.autocomplete.AutoComplete.get_entity。VulnCheck 也发布了独立分析文章。虽然 Picklescan 本身 Star 数较低，但它是许多 ML 安全流水线的关键组件，绕过影响可能很大。

修复建议：

  • 升级 Picklescan 到 0.0.29 或更高版本
  • 不要仅依赖 Picklescan，采用多层防御策略（沙箱执行、签名验证等）
  • 审查 pickle 文件来源，实施来源信任机制
  • 考虑使用更安全的序列化格式（如 safetensors）替代 pickle

🟡 MCP Documentation Server: Web UI API Binds to All Interfaces Without Auth

High ⭐ 340 🔴 PoC Available 📖 详细分析

漏洞描述：@andrea9293/mcp-documentation-server v1.13.0 的 Web UI 在端口 3080 自动启动，但默认绑定到所有网络接口（0.0.0.0:3080）而非仅 localhost，且其文档管理 API 端点不需要任何认证。这意味着同一局域网、VM 网络或容器网桥上的任何客户端都可以无需凭据即访问文档管理 API。

影响产品：MCP Documentation Server ⭐ 340

影响版本：= 1.13.0

修复版本：1.13.1

攻击面：所有运行该 MCP 文档服务器的开发者和团队，特别是在共享网络环境中部署的实例。任何与服务器处于同一网络的设备均可访问。

触发条件：

  • 使用 @andrea9293/mcp-documentation-server v1.13.0
  • 服务器运行在共享网络环境（局域网、云 VPC、容器网络）
  • 攻击者与服务器处于同一网络段

潜在危害：

  • 未授权读取/修改/删除文档内容
  • 窃取敏感的开发文档、API 密钥、内部笔记
  • 注入恶意内容到文档中，实现供应链攻击
  • 在 MCP 生态中建立立足点，进一步横向移动

可利用性：有完整 PoC。公告作者成功复现了漏洞——在同一网络中直接访问 3080 端口即可操作文档管理 API。攻击方法简单（仅需访问 TCP 端口），无需任何凭据或特殊技术。

修复建议：

  • 升级到 1.13.1 或更高版本
  • 手动配置绑定地址为 127.0.0.1（如版本支持）
  • 在网络层面限制 3080 端口的访问
  • 审查是否已有敏感文档被未授权访问
