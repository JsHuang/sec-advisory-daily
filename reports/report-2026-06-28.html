🔴 pnpm: Path traversal in configDependencies env lockfile allows symlink creation outside node_modules
GHSA-qrv3-253h-g69c | CVE: 待分配
优先级: 紧急
High ⭐ 35,636 🔴 PoC Available 📖 详细分析

漏洞描述：pnpm 在处理 env lockfile 的 configDependencies 部分时，直接使用包名创建符号链接，未对路径遍历进行验证。攻击者可以通过构造包含 ../ 的恶意包名，在 node_modules/.pnpm-config 目录外创建符号链接，实现文件系统写入原语。

影响产品：pnpm ⭐ 35,636

影响版本：< 10.34.4 和 >= 11.0.0, < 11.7.0

攻击面：供应链攻击 - 攻击者提交包含恶意 pnpm-lock.yaml 的项目到公共仓库，受害者克隆并执行 pnpm install 即可触发。

触发条件：

  • 受害者克隆包含恶意 lockfile 的项目
  • 执行 pnpm install（即使使用 --ignore-scripts）
  • 无需用户交互，自动触发

潜在危害：

  • 在项目目录外创建符号链接，可能覆盖关键系统文件
  • 结合其他漏洞可实现远程代码执行
  • 供应链攻击可大规模传播，影响整个开发团队
  • 绕过 --ignore-scripts 安全机制

可利用性：有完整 PoC 代码和详细利用步骤。攻击者只需：

  1. 创建包含恶意 configDependencies 的 lockfile
  2. 提交到 Git 仓库
  3. 诱导受害者克隆并安装依赖

漏洞原理：pnpm 代码中直接使用 path.join(configModulesDir, pkgName)，未对 pkgName 进行路径遍历检查。当 pkgName 包含 ../ 时，path.join 会解析到父目录，导致符号链接创建在预期位置之外。

PoC 示例：

# 恶意 lockfile 配置
importers:
  .:
    configDependencies:
      legit-config-dep:
        specifier: '1.0.0'
        version: '1.0.0'
      '../../PWNED_CFGDEP':
        specifier: '1.0.0'
        version: '1.0.0'

# 执行结果
[+] Traversal sink status: symlink -> ../store/v11/PWNED_CFGDEP/1.0.0/PWNED_CFGDEP
[VULNERABLE] pnpm created/modified a path outside node_modules/.pnpm-config

修复建议：

  • 立即升级到 pnpm 10.34.4 或 11.7.0+
  • 审查项目中的 pnpm-lock.yaml 是否包含可疑路径
  • 不要随意克隆和执行未知来源项目的依赖安装
  • 考虑使用 pnpm-lock.yaml 签名验证机制

🟠 pnpm: `patch-remove` could delete project-selected files outside the patches directory
GHSA-72r4-9c5j-mj57 | CVE: 待分配
优先级: 高危
High ⭐ 35,636 📖 详细分析

漏洞描述：pnpm 的 patch-remove 命令在处理补丁条目时，未正确验证路径是否超出配置的补丁目录范围。攻击者可以构造恶意补丁条目，利用路径遍历或绝对路径，导致 pnpm patch-remove 删除项目外的任意可达文件。

影响产品：pnpm ⭐ 35,636

影响版本：< 10.34.4 和 >= 11.0.0, < 11.7.0

攻击面：本地攻击 - 需要攻击者能够修改项目的 patchedDependencies 配置，或在恶意项目中预设补丁配置。

触发条件：

  • 项目包含恶意的补丁配置
  • 用户执行 pnpm patch-remove 命令
  • 补丁路径解析到补丁目录之外

潜在危害：

  • 删除项目外的关键文件（如配置文件、源代码）
  • 通过嵌套符号链接实现更深层的路径逃逸
  • 可能删除系统文件或用户数据
  • 破坏项目完整性，导致开发环境损坏

可利用性：有详细的漏洞原理说明和利用重放步骤。攻击场景包括：

  1. 直接路径遍历：使用 ../../../ 逃逸
  2. 嵌套符号链接：创建指向外部的符号链
  3. 悬空符号链接：利用 realpath() 的 ENOENT 错误

漏洞原理：原代码在删除补丁前未进行完整的路径验证。修复方案引入了组件感知的包含检查（isSubdirectory.ts），在删除前验证：

  • 拒绝遍历路径和绝对路径
  • 规范化父目录路径
  • 解除链接时不跟踪最终符号链接
  • 批量验证所有补丁后再执行删除

修复建议：

  • 立即升级到 pnpm 10.34.4 或 11.7.0+
  • 审查项目中的补丁配置，确保路径合法
  • 在执行 patch-remove 前检查补丁列表
  • 避免在不受信任的项目中执行补丁操作

🟠 pnpm: Hoisted install imports lockfile alias outside node_modules
GHSA-fr4h-3cph-29xv | CVE: 待分配
优先级: 高危
High ⭐ 35,636 📖 详细分析

漏洞描述：pnpm 在处理提升安装（hoisted install）的依赖别名时，未正确验证别名是否包含路径遍历组件或保留名称。攻击者可以构造恶意 lockfile，使用遍历别名将包文件安装到 node_modules 目录外，或使用保留别名（如 .bin、.pnpm）覆盖 pnpm 自身的布局结构。

影响产品：pnpm ⭐ 35,636

影响版本：< 10.34.4 和 >= 11.0.0, < 11.7.0

攻击面：供应链攻击 - 攻击者提交包含恶意别名的 lockfile，受害者使用提升安装模式时触发。

触发条件：

  • 项目使用提升安装模式（hoisted mode）
  • lockfile 中包含恶意依赖别名
  • 执行 pnpm install

潜在危害：

  • 将恶意包文件安装到项目外
  • 覆盖 pnpm 内部结构（.pnpm、.bin）
  • 可能劫持其他包的执行路径
  • 结合路径遍历可写入任意目录

可利用性：有详细的漏洞原理说明和利用重放步骤。攻击者需要：

  1. 构造包含遍历别名的 lockfile
  2. 诱导受害者使用提升安装模式
  3. 执行 pnpm install 即可触发

漏洞原理：原代码在构建提升依赖图时，直接使用依赖名称作为路径组件，未进行安全检查。修复方案在 TypeScript 和 Rust 实现中都引入了安全连接助手（safeJoinModulesDir），验证：

  • 拒绝遍历路径、绝对路径、平台特定路径
  • 拒绝保留包名（.bin、.pnpm 等）
  • 返回 ERR_PNPM_INVALID_DEPENDENCY_NAME 错误

修复建议：

  • 立即升级到 pnpm 10.34.4 或 11.7.0+
  • 如果使用提升安装模式，审查 lockfile 中的别名
  • 考虑使用非提升模式（默认）以获得更好的隔离性
  • 监控 lockfile 变更，使用 Git 审查机制
